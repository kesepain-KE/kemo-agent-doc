# kemo-agent 1.0.2 — 记忆链路修复版：让潮汐记忆真正开始涨潮

1.0.1 回答的是"这条主链路到底牢不牢"；1.0.2 回答的是另一个更具体的问题——**记忆系统里那些本该自己运转的链路，为什么悄悄停摆了**。

这一版的四件事全部来自真实运行中发现的问题：热画像巡检每次都要逐条读取碎片、几百条碎片必然触发工具次数上限；搜索只认整句连续匹配、候选句子永远搜不到已有碎片，于是"同一件事反复新建碎片、已有碎片从不加权"；热画像输出稍微长一点就被整体拒绝；晋升遇到大批到期碎片只能一批全跑、一批失败全断。

修复之后，记忆的四个链路各自恢复了它本来的样子。

---

## 巡检：从逐条读取到批量分页

`memory_temporary_important` 子代理的巡检原本是"分页列出文件名 + 逐条 `get` 正文"——碎片少的时候没问题，但临时记忆增长到一百多条后，一次巡检需要约 188 次工具调用，而子代理工具循环上限是 20 次，**必然超限**。失败后按契约保留旧热画像，而旧热画像又曾被误清空，链路从此空转，热画像长期是占位文本。

修复：`memory_manage` 的 `list` 新增两个参数——

- `include_content`：条目直接附带完整正文，不再需要逐条 `get`；
- `page_char_limit`：按字符预算分页（默认 80000），返回 `page_limited_by_chars` / `next_offset`，与条数分页双边界配合。

巡检现在用 `list(limit=500, compact=true, include_content=true, page_char_limit=80000)` 一次拿全三层临时记忆与永久记忆，**工具调用从 ~188 次降到 3~5 次**，不再触碰任何上限。

## 搜索：从整句匹配到分词命中（加权链路的关键修复）

这是 1.0.2 最隐蔽也最重要的一处。`search_by_title` / `search_by_content` / `search_many` 此前是**整串连续子串匹配**：查询「Git 提交 独特更新说明 无表情包」必须完整出现在标题或正文里才算命中。self_improve 按指引提交的正是这种完整候选句子，于是——**永远 0 命中**。

0 命中的后果是连锁的：模型判定"未命中已有碎片"→ 每次聊天都为同一个事实新建碎片（Git 提交风格碎片一度累积 30+ 条）→ 已有碎片从不被加权 → `memory_weight_events` 加权事件表几乎为空 → 权重全部为 0 → 无法晋升、到期即删。**长期记忆的构建实际上从未启动过。**

修复：搜索升级为**分词多关键词匹配**——

- 英文/数字按整词切分（`[a-z0-9]+`），中文连续段生成 bigram；
- 整串包含优先，词命中与 bigram 覆盖率评分排序；
- 命中返回 `match_score` / `match_coverage` / `exact_match` / `matched_terms` / `field_scores`。

同一查询现在能命中 16 条相关碎片。配合 self_improve 指引更新（候选提炼为 2~4 个核心关键词、命中必须复制已有文件名返回同名 upsert），**每日加权链路恢复**：同一事实再次出现时加权 +1，而不是再建一个新碎片。顺带完成了 33 条重复碎片的整理归并。

## 输出上限：注入预算与防失控上限解耦

`important_memory_max_chars`（5000）的本职是**Prompt 注入字符预算**——热画像进入上下文的显示上限，文件本身可以更长。但 executor 把它误当成模型输出的硬性校验：输出 6762 字符就整体拒绝，热画像不更新。

修复：新增独立配置 `important_memory_output_max_chars`（默认 20000）：

- 5000 回归注入截断本职（`run/prompt.py` 已正确截断，文件完整落盘）；
- 5000~20000 字符的合理加长正文正常落盘，不再被误拒；
- 超过 20000 才拒绝并提示精简，防止模型失控重复。

## 晋升：从一批全跑到期满必达

`review_due` 的晋升扫描此前把所有到期达标碎片一次性提交给 self_improve——碎片多了以后单批必然超时或超限，一批失败整轮全断。运行手册要求的"处理本轮全部到期且达标碎片"从未真正实现。

修复：新增 `_promotion_batches` 分批处理——按目标层分组（普通层每批最多 20 条、永久层每批最多 8 条），每批独立调用子代理、独立事务落盘，单批失败不阻塞其余批次，未成功条目保持原层由后续 30 秒扫描重试。批次结果记录 `batch` / `requested` / `applied` / `status`（completed / partial / failed）。

## 插件与运行时：顺路补齐

- **file 插件**：`list_dir` / `tree_dir` 支持 limit/offset 分页与 `next_offset` / `has_more` 元数据，目录条目从旧上下文压缩省略；新增忽略目录清单与二进制扩展名清单，目录列举与搜索自动跳过；
- **shell 插件**：Windows 失败提示——`head` 不可用提示改用 `Select-Object -First` 或 file.read_range、`Get-FileHash` 缺失提示改用 certutil、命令不存在识别；`mkdir` 等命令返回明确的路径已存在/不存在结果；
- **运行时**：`agents.rounds_after_compression 不能大于 agents.max_rounds` 校验；工具调用组构建；子代理请求内 item / 工具调用 ID 类别标识。

## 从 1.0.1 到 1.0.2

| 链路 | 1.0.1 | 1.0.2 |
|------|-------|-------|
| 热画像巡检 | 分页 list + 逐条 get，~188 次调用必超限 | list 批量正文 + 字符预算分页，3~5 次调用 |
| 碎片搜索 | 整串连续子串匹配，长句永远 0 命中 | 英文整词 + 中文 bigram 分词评分，加权链路恢复 |
| 热画像输出 | 5000 字符硬性拒绝，合理加长被误拒 | 注入预算 5000 与防失控上限 20000 解耦 |
| 记忆晋升 | 全部候选一批提交，一批失败全断 | 按目标层分批，单批失败不阻塞、未成功重试 |
| 重复碎片 | 同一事实反复新建，30+ 条同主题 | 命中已有碎片按日加权，碎片收敛 |

## 写在最后

1.0.0 让主生态闭环，1.0.1 让主链路经过系统性复核，1.0.2 让记忆系统的四条内部链路各自转起来。

最大的收获不是"修好了什么"，而是确认了一个容易被忽视的事实：**一条链路只要静默失败，它带来的问题不会报错，而是悄悄累积**——碎片越来越多、权重全部为零、热画像只剩占位符。这类问题只有靠"检查数据本身"才能发现：加权表为什么没有新记录？同主题碎片为什么越来越多？

现在四条链路都有了明确的运转证据：巡检成功重建热画像、搜索命中后加权表开始增长、输出超限只拦失控、晋升分批必达。潮汐记忆从此真的开始涨潮。
