# kemo-agent 1.0.3 — 动态 Prompt 段刷新：让每一次模型请求都看到最新世界

1.0.2 回答的是"记忆链路为什么悄悄停摆"；1.0.3 回答的是另一个同样隐蔽的问题——**一轮对话跑得越久，模型看到的感知与拓展数据就越旧**。

在一轮对话里，工具可能被调用十几次，运行中引导可能追加新内容，上下文超限后还会压缩重试。而旧版本的系统 Prompt 在一轮开始时构建一次，之后全程复用：第一个请求时采集到的天气、网关状态、设备水位，到第十次工具续轮时已经陈旧；压缩重试后，模型甚至可能对着几分钟前的数据继续推理。

这一版把 System Prompt 拆成了两种生命周期：**静态段一轮一构建，动态段一次请求一刷新**。

---

## 静态段与动态段

`build_prompt_bundle()` 仍然在一轮用户对话开始时构建完整的 15 段 Prompt，包括人格、运行手册、子代理与插件注册、知识索引、记忆和任务计划——这些内容一轮内基本不会变，构建一次是合理的。

变化的是最后两段：

- `[expand_data]`（三层拓展的健康数据与操控手册注入层）；
- `[perception]`（全局感知模块采集文件）。

它们属于 `DYNAMIC_PROMPT_SECTION_NAMES`，由新增的 `refresh_dynamic_prompt_bundle()` 管理：**在每一次逻辑 Provider 请求前**，从当前磁盘重新读取后台采集器已经发布的最新快照，替换掉 bundle 中的旧动态段，再交给 Provider。

于是：

- 首个模型请求用的是对话开始时的最新采集；
- 工具续轮、运行中引导续轮，用的是当时的最新采集；
- 上下文超限压缩后的重试，用的仍然是当时的最新采集。

## 请求前刷新，但不在传输层改正文

实现上有一个明确边界：刷新发生在**逻辑请求**之间，而不是**网络传输**之间。

`conversation_runtime` 在每个 Provider 迭代开始、以及同一逻辑请求每次重试前调用 `refresh_dynamic_system_message()`，替换 `messages[0]` 的 system 消息并同步提交器上下文。而 Provider 适配器对同一个网络请求的传输重试、SSE 续传，继续复用已经生成好的请求正文——不会在传输中途改变 Prompt，避免续传与正文不一致。

## 不采集，只读快照

动态刷新**不执行 `data_update.py`**，也不触发任何采集脚本。它只读取后台采集器已经写好的 `input_data.md` / `sense.md` 等快照文件，因此：

- 采集频率与超时仍由 RuntimeHost / Cron 统一调度，不被请求线程改变；
- 刷新本身是纯文件读取，不会把采集耗时叠加到每一次模型请求上；
- 后台采集器与请求线程之间不需要锁或队列，读旧一点的数据也不会破坏一致性。

## 从 1.0.2 到 1.0.3

| 维度 | 1.0.2 | 1.0.3 |
|------|-------|-------|
| Prompt 生命周期 | 一轮一构建，全程复用 | 静态段一轮一构建，动态段一次逻辑请求一刷新 |
| 动态段范围 | 无 | `[expand_data]` 与 `[perception]` |
| 工具续轮数据 | 本轮开始时的旧快照 | 每次请求前的最新已发布快照 |
| 上下文恢复重试 | 复用旧正文 | 重试前刷新动态段（传输层重试仍复用正文） |
| 采集执行 | 与请求构建解耦 | 请求构建只读快照，仍不执行采集 |

## 开始使用

```bash
cd kemo-agent
git pull
python update.py --module all
```

更新完成后，请完整重启 kemo-agent，使新的 Python 运行时与 Web 前端构建一起生效。

::: tip 升级提示
1.0.3 没有新增配置项，也不需要调整任何现有配置。动态刷新只对 `expand_data` 与 `perception` 生效，其余 Prompt 段行为与 1.0.2 完全一致。
:::

## 写在最后

1.0.2 让记忆链路恢复运转，1.0.3 让"外部世界"在长对话中保持新鲜。

这两版有一个共同的主题：**长期运行的智能体，最大的敌人是静默的陈旧**。记忆碎片从不加权不会报错，只是悄悄不涨；感知数据停在对话开始也不会报错，只是模型越来越"瞎"。修复它们的共同方法是：让数据流真正动起来——记忆靠每日加权证据，Prompt 靠请求级快照刷新。

从这一版开始，模型在工具链的最后一环看到的天气、水位和网关状态，与它看到的第一个请求一样新鲜。
