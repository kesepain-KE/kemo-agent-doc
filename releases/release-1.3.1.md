# v1.3.1 四渠道一键部署与独立部署器

## 这一版在解决什么

v1.3.1 只做一件事：**让 kemo-agent 能被四种方式一键装起来，并且装完之后还能持续更新。**

在此之前，部署只有一条路——克隆源码、跑 `setup.py`、再启动 `start_web.py`。这条路对开发者没问题，但对"只想把智能体跑起来"的人门槛偏高：要 Git、要 Node 构建前端、要自己盯依赖。这一版把部署从框架里独立出来，做成一个可以单独演进的部署器，同时给出 Windows、Linux、npm、Docker 四条入口。

## 部署器：独立于框架之外

部署器放在 `deploy/`，有一条硬边界——**不导入主框架任何模块，也不改动主框架任何文件**。原因是它要能在"目标树还不存在"的时候运行：首装时应用还没落地，它不能假设任何东西可用。

因此它自带全部能力，并且只依赖 Python 标准库，连 YAML 解析都自己实现了一份：拉取发布包、校验摘要、解压、按映射铺开、保留用户数据、失败回滚、断点恢复，全部自己完成。

它与应用更新器的分工也划清了：应用更新器管"更新我自己"，属于运行中的数据卷；部署器管"把某个版本铺到某个目标"，属于包卷。两者不共享代码，互不干扰。

## 四条入口，两种更新方式

四条入口都从同一份 GitHub Release 资产安装，因此版本只有一个真相——根目录的 `version.json`：

- **Windows / Linux** 用一条命令拉起安装脚本，装到用户主目录下的 `.kemo-agent`。更新就是把**同一条命令再跑一遍**，脚本自己判断版本，决定装还是升。
- **npm** 从 Release 资产直装，更新是**重跑同一条命令**（URL 里的 `latest` 永远指向最新版）；**Docker** 走包管理器，更新是**换一个版本号**：`docker compose pull && docker compose up -d`。

两种方式的共同点是：**程序文件跟着包走，用户数据原地不动。** 聊天历史、记忆、自建拓展与感知、凭据、配置全部受保护清单保护，升级时只覆盖代码。

## 安装包长什么样

发布资产是 `kemo-agent-release-<version>.zip`，附带同名 `.sha256`。包里顶层是清单文件与 `tree/`，`tree/` 内是完整的应用树——**包含预构建好的前端**。这是关键：目标机不需要装 Node，也不需要自己构建网页端。

包里排除了运行态与私有内容：`.git`、开发临时目录、`tmp`、`users`、`runtime`、`.env`。

## 保护数据是第一位的

部署器把"哪些绝不能碰"列成了硬清单，而且**只能追加、不能解除**：

- `users/`、`runtime/`、`.env`、`message/out/` 里的用户数据与凭据；
- 模块自己的配置值与状态文件；
- 数据库、绑定关系与运行配置。

配置文件按"按键路径保留旧值、只补新键"的方式合并，类型或结构冲突时直接拒绝更新，而不是静默覆盖。更新带持久化事务，中途失败会回滚；进程被强杀留下未完成事务时，用 `recover` 命令恢复。

保留两次成功备份，但**不提供数据库逆向迁移**——不能把代码降级当成完整的数据恢复，重要数据仍应另行备份。

## 这一版还同步了什么

- 版本面升至 1.3.1：根版本、四组件、中英 README 徽章、前端 `package.json` 与版本校验脚本一致更新。
- 全局知识库新增《一键部署、日常运维与发布》专题，并补进主索引。
- 前端构建产物确认进包；模块扫描的边界合同补上部署器测试工作目录，避免本地副本被误判为生产代码。
- 部署器的正式测试并入主测试套件，与原有开发期套件分离。

## 验证

这一版进过完整的发布前检查：版本一致性、开发期分层验收、正式后端测试、模板合同、编译检查、补丁格式、前端测试与生产构建，**八个阶段全部通过**。部署器自身有独立的正式测试套件（含故障路径），全部通过。CI 与 Security 检查全部通过。

需要说明的是：**安装入口实现完成，不等于所有渠道都已线上发布。** 远程安装脚本、临时 npm 包与 Docker 镜像需要分别发布，Release 资产需要上传——这些是发布动作，不是提交代码。本版已完成 Release 资产的构建与上传；npm 与 Docker 的分发另行进行。
