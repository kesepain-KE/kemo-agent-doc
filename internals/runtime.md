# 运行原理

一次请求先进入 `run/engine.py` 的稳定公共门面，再由 `conversation_runtime.py` 与各领域模块协同编排。不同入口共享同一条核心链路，并通过统一事件协议向调用方返回文本、推理、工具、用量、错误和结束状态。

## 完整流程

```text
请求（user + source + session_id）
  → engine 公共门面与请求规范化
  → 加载全局默认和用户配置，创建 Provider
  → 获取会话锁，准备归档与临时工作区
  → 审核到期记忆
  → 构建 17 段 PromptBundle 和工具注册表
  → 按轮次与 Token 预算选择上下文
  → 必要时生成摘要并重新选择，直到稳定
  → Provider → 工具 → Provider 循环
  → 消费运行中引导
  → 成功提交历史
  → 为实际注入的记忆加权，登记或执行记忆提取
```

## 会话锁

锁的维度是 `(source, user, session_id)`。同一会话的请求串行执行，避免两个并发请求同时覆盖历史；不同用户或会话仍可并行，但共享全进程 Provider 并发闸门。

## Provider 与工具循环

每轮 Provider 响应若包含工具调用，运行时校验参数、执行工具，并把结果作为下一次模型输入。相同工具名和完整参数构成调用签名；缓存和连续调用保护用于避免副作用重复执行。

运行中引导进入会话专用队列，在 Provider 返回或工具完成后的安全边界追加。它不会中断已经阻塞的 Provider 或工具函数。

工具的外层看门狗期限由工具清单策略决定。普通工具使用显式有效 `timeout` 或全局默认值；子代理调度工具使用子代理整体期限。工具超时会发送工具专属取消信号，不会自动取消整轮对话。

## 提交边界

只有模型和工具循环正常完成后，运行时才提交历史、更新用量指标、为记忆加权并触发记忆管线。Provider 错误、取消或超时不会留下伪造的完整轮次，也不会给记忆加权。

::: tip 派生缓存
上下文摘要和 Web 会话卡片摘要都是可重建缓存，不替代完整归档。缓存失败不应破坏原始历史。
:::
